.. _reference-init-deployment-script:

init-deployment.sh Script Reference
===================================

``init-deployment.sh`` initializes a Dioptra deployment.
The script is located in the root of the deployment directory generated by the Dioptra template.

.. seealso::

   For step-by-step instructions, see :ref:`how-to-prepare-deployment`.

Syntax
------

.. code:: text

   ./init-deployment.sh [--enable-postgres-ssl] [--skip-rustfs-setup]
                        [--branch BRANCH] [--worker-ssl-service {tfcpu|pytorchcpu}]
                        [--python CMD] [--help]

Square brackets indicate optional arguments.
Braces with vertical bars indicate a required choice when supplying that option.

.. _reference-init-deployment-requirements:

Requirements
------------

The command requires:

* Bash.
* Python 3.11 or newer with the ``jinja2`` package installed.
* Docker with Docker Compose.
* The container images configured for the deployment.
* A POSIX environment supporting descriptor-relative file operations, same-directory hard links, and file/directory synchronization.

Run the command from the deployment directory as the user who owns its files and has permission to use Docker.
The deployment user needs permission to read and create files and change their permissions.

The normal deployment must be torn down before initialization.
The script refuses existing runtime containers, including stopped containers, before changing files or volumes.
Use ``docker compose down`` without ``--volumes`` to retain persistent data.

Options
-------

.. program:: init-deployment.sh

.. option:: --enable-postgres-ssl

   Enable PostgreSQL TLS using ``ssl/db/server.crt`` and ``ssl/db/server.key``.
   Disabled by default. Include it on every initialization run that should retain PostgreSQL TLS.

.. option:: --skip-rustfs-setup

   Skip RustFS service setup.
   Disabled by default.
   Useful for configuration changes that do not require reconciling storage accounts and policies.
   RustFS account initialization can also be rerun without duplicating policy attachments.

.. option:: --branch <branch-name>

   Dioptra GitHub branch used when syncing built-in task plugins and frontend files.
   The default is ``main``.
   Select the branch matching your container images, such as ``main`` for releases or ``dev`` for development builds.

.. option:: --python <cmd>

   Host Python interpreter command.
   Defaults to ``.venv/bin/python`` in the deployment directory when available, otherwise ``python``.

.. option:: --worker-ssl-service <tfcpu|pytorchcpu>

   Container image used to bootstrap worker SSL named volumes.
   The default is ``tfcpu``.

.. option:: -h, --help

   Print help and exit.

Examples
--------

Replace ``BRANCH_NAME`` in these examples with the Dioptra branch matching your container images.

Initialize the deployment:

.. code:: sh

   ./init-deployment.sh --branch BRANCH_NAME

Initialize the deployment with PostgreSQL TLS enabled:

.. code:: sh

   ./init-deployment.sh --branch BRANCH_NAME --enable-postgres-ssl

Rerun after configuration changes that do not need RustFS account reconciliation:

.. code:: sh

   ./init-deployment.sh --branch BRANCH_NAME --skip-rustfs-setup

Output and Exit Status
----------------------

The script prints initialization progress and error messages.
Initialization reports the deployment's HTTPS address, public CA certificate path and SHA-256 fingerprint, certificate expiration dates, and any shortened certificate lifetime.

Successful initialization and ``--help`` return zero.
Failed initialization, HTTPS verification, worker registration, or service teardown returns a nonzero exit status.

An interrupted certificate operation reports its operation ID and the applicable :ref:`recovery command <how-to-recover-certificate-operation>`.

Initialization Behavior
-----------------------

The ``init-deployment.sh`` script automates the following initialization steps:

- Generates random passwords used to secure Dioptra's services
- Generates or validates API/nginx certificates and installs trusted CA certificates in the containers
- Copies configuration files and certificates into named volumes
- Sets appropriate file and folder access permissions
- Initializes the persistent API signing key before database migrations and API startup
- Creates RustFS S3 accounts and configures their access permissions
- Syncs built-in task plugins from the Dioptra GitHub repository
- Enables SSL/TLS in PostgreSQL (if applicable)

The script installs certificates while normal deployment services are stopped.
It then starts normal services, verifies live HTTPS, and registers the worker account.
Before returning, it tears down the initialization and runtime services it started while retaining volumes, credentials, certificates, and recovery files.
On failure, it attempts the same teardown and reports any teardown failure.
Normal operation starts separately with ``docker compose up -d``.

Files
-----

The following sections describe the files managed by initialization, including their locations and how the script handles them on subsequent runs.

.. _reference-init-deployment-credentials:

Host Credential Files
~~~~~~~~~~~~~~~~~~~~~

The following paths are relative to the deployment directory and form one credential set:

* ``.env``
* ``secrets/postgres-passwd.env``
* ``secrets/<deployment-slug>-rustfs-accounts.env``

.. list-table:: Credential-set handling
   :header-rows: 1
   :widths: 40 60

   * - Condition
     - Result
   * - All three files are absent.
     - Generate the complete set with mode ``0600`` (owner read/write only).
   * - All three files exist and are nonempty.
     - Preserve contents and ownership, repair permissions to ``0600`` and report repairs without logging credentials.
   * - The set is incomplete or empty, or a path is linked, nonregular or cannot be secured.
     - Stop initialization.

Existing values are not checked for consistency across files or against running services.

An interrupted run can leave incomplete credentials or temporary files containing secrets.
See :ref:`how-to-recover-deployment-credentials` before removing files or rerunning initialization.

.. _reference-init-deployment-signing-key:

API Signing Key
~~~~~~~~~~~~~~~

The API signing key is stored in the persistent REST API data volume and retained across container restarts.
Initialization creates the key when it is absent and preserves an existing valid key.
If key initialization fails, the script stops before database migrations or API startup.

.. _reference-init-deployment-certificates:

API and nginx Certificates
~~~~~~~~~~~~~~~~~~~~~~~~~~

Initialization uses ``config/ssl.toml`` and calls :ref:`scripts/manage_ssl.py init <reference-manage-ssl-init>` to prepare and install certificates for the API and nginx.
By default, it creates a deployment CA and separate server certificates and private keys for the two services.
To use your own server certificates, follow :ref:`how-to-enabling-ssl-tls`.

Rerunning initialization preserves valid existing certificates and private keys.
Changes to supplied certificate files or the ``source`` setting require :ref:`certificate replacement <how-to-replace-deployment-certificates>`.
See :ref:`manage_ssl.py init <reference-manage-ssl-init>` for validation and file-permission handling.

The public certificate for a Dioptra-generated CA is saved at ``ssl/ca-certificates/dioptra-local-ca.crt``.
Browser and Python-client trust are configured separately; see :ref:`how-to-adding-certificates`.

:ref:`reference-certificate-policy` lists file-permission and expiration requirements.
:ref:`reference-deployment-certificate-backups` identifies the files to back up.
